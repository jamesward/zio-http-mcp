# Agent Guidelines

## Spec compliance and client quirks

This rule is a hard requirement. Every change to server or client behavior has to follow it.

- **Defaults follow the spec.** With no options set, the server and the client behave as the published MCP revision and its extensions say. A spec MUST is never optional in the defaults.
- **The spec is the truth, not the conformance kit.** The kit (`ConformanceSpec`, `ClientConformanceSpec`) can lag the spec, run ahead of it, or get it wrong. Before changing behavior to pass a check, read the spec text the check cites. If the kit and the spec disagree, follow the spec. Then baseline or filter that check, with a comment quoting the spec and naming the kit version.
- **Deviations live in quirks modes.** When a real client or server does something other than the spec (Claude, ChatGPT, the MCP TypeScript, Python and Java SDKs, Inspector, `@ai-sdk/mcp`, Mastra, TanStack, and so on), don't bend the default to fit it. Add a quirk instead:
  - The quirk is an explicit opt-in setting, named for what it does. Model it on `McpEventsCompatibility`: `Spec` is the default, and `KnownClients` adds the workarounds.
  - It applies only to the clients that need it. Key it on what identifies the client (`clientInfo` name, `User-Agent`, declared capabilities), so a client that follows the spec still gets the spec with quirks on. Once a client declares the spec behavior (for example, by declaring the extension), it gets the spec.
- **Every quirk is documented.** Each one gets a README entry naming the client and its version, the date it was seen, what differs from the spec, and the setting that turns it on. Each one also gets a scaladoc on the setting.
- **Every quirk is tested.** Each one has a test that runs it against that client, with the real client in a container where possible, as `AiSdkEventsSpec` does. A second test checks that the default stays spec-compliant for the same request.
- **Never break deployed clients.** Before making a default stricter, run the interop specs (`PythonSdkSpec`, `JavaSdkAuthSpec`, `JavaSdkClientSpec`, `TypeScriptSdkDiscoverySpec`, `TachyonInteropSpec` and the `*EventsSpec` client specs) and check the clients we know are deployed, Claude and ChatGPT above all. If the stricter default would break a client that works today, ship the quirk in the same change. Name it in the README's upgrade notes, so a server for that client knows which setting to turn on.
- **Invalid input from a peer is refused, one item at a time.** When a server or client sends something the spec rules out (a tool whose `inputSchema` isn't an object, an invalid `x-mcp-header`), refuse that item with a warning and keep the rest, as the spec does for `x-mcp-header`. Don't coerce it into something valid: that changes what the peer said. A peer that needs it accepted gets a quirk.
- **Kit bugs are not quirks.** A check that a spec-compliant implementation can't pass is a kit bug, as when `wire-schema-valid` checks `CreateTaskResult` against the `CallToolResult` schema. Don't change the defaults for it, and don't add a quirk mode for it. Baseline it as described above.

## README Examples

Every code example in README.md must have a corresponding test. Tests live in:

- `McpToolSpec` — for tool DSL examples (`.handle`, `.handleWithContext`, error handling, etc.)
- `AuthSpec` — for authorization examples (`.auth(...)`, `ctx.principal`, `.requireScopes(...)`)
- `StaticBearerSpec` — for the bearer-only server example (`StaticBearer.aspect`): JSON-RPC error instead of 401, token accepted and rejected, notifications and GET, and `open = Handshake`
- `TokenVerifierSpec` — for `TokenVerifier.discoverJwks` / `.jwks` / `.introspection` behavior
- `LiveAuthSpec` — for end-to-end DCR + token + tool-call validation (raw HTTP) against `login.jamesward.dev`
- `JavaSdkAuthSpec` — for end-to-end Java MCP SDK interop with a bearer token against `login.jamesward.dev`
- `McpSkillsJarsSpec` — for the SkillsJars example (`McpSkillsJars.load`, serving classpath skills), exercised against real SkillsJars declared as test-scope dependencies in `build.sbt`
- `McpAppsSpec` — for the MCP Apps examples (`McpApps.tool` / `resourceHandler` / `result`, view and app-only tool metadata, global entry points under `openai/ui`, `preferredDisplayMode`, `McpApps.claudeDomain`, `McpApps.clientSupportsHtml`)
- `McpClientSpec` — for client examples (`McpClient.connect`, `listTools`, `callTool`, resources, error handling) against our own `McpServer` over loopback HTTP; also covers the legacy-pinned (`preferredVersion = V2025_11_25`) client
- `McpClientModernSpec` — for the modern (2026-07-28) client examples: `server/discover` negotiation, stateless calls, the `onInputRequest` (MRTR) example, the multi-round exchange where the client echoes the server's `requestState`, and `-32021` for a client without `onInputRequest` (which declares no input capabilities)
- `NegotiationSpec` — for protocol version negotiation: era detection, header validation, the required per-request `_meta` (`-32602` + `400` without `protocolVersion` or `clientCapabilities`), `server/discover`, the modern result envelope, version/header error responses, modern request-scoped notification streaming (`_meta.progressToken` / `_meta.io.modelcontextprotocol/logLevel` → SSE), and MRTR (SEP-2322) — keyed `inputRequests`/`inputResponses`, `ctx.inputs` batching, signed `requestState` across rounds and its rejection when tampered, `McpRequestStateStore` (a shared secret letting two servers serve each other's rounds, the `McpServer.State` layer supplying one store to every server on it, independently keyed stores refusing each other, and a server-side store handing out handles), capability-gated input, input the client didn't declare (`-32021` + `400` with `data.requiredCapabilities`), malformed `inputResponses`, and `prompts/get` asking for input
- `TasksSpec` — for the Tasks extension examples (`io.modelcontextprotocol/tasks`): enabling tasks with `withExtensions(McpTasks...)` (and nothing without it), a custom `McpTaskStore`, `.taskExecution(...)` server-directed creation gated on the client's declared capability (and `WhenSlow`: a plain result for a quick call, a task for a slow one, cancellation during the grace period), `pollSchedule` (the suggested `pollIntervalMs` growing with the task's age, and `TaskPolicy.pollIntervalAt`), the flat `CreateTaskResult` / `tasks/get` shapes, completed/isError/failed/cancelled, `input_required` answered with `tasks/update`, progress as `statusMessage`, TTL expiry, `-32021`, `Mcp-Name: <taskId>`, scope enforcement, binding a task to its creator, `notifications/tasks` on `subscriptions/listen` (agreed only for the caller's live tasks), and the client's `callTool` / `startTool` / `getTask` / `awaitTask` / `cancelTask`
- `McpEventsSpec` — for the Events extension examples (`io.modelcontextprotocol/events`, SEP-3415, experimental): `McpEvent(...).buffered` over an `McpEventBuffer` (per-subscriber filtering) and `.check` (the `clock.tick` check function in `EventFixtures`, shared with `StdioServerMain` and the conformance fixture), `events/list`, `events/poll` (bootstrap from a null cursor, `maxEvents`/`hasMore`, `truncated` for a stale or foreign cursor and for `maxAgeMs`, `nextPollMs`), `events/stream` (`active`, events and heartbeats with the subscription id, backlog replay, `error` vs `terminated` and the final result, closing the stream ending the subscription), errors (`-32023`, `-32602`, `-32026` for `pollOnly`, `Mcp-Name` required: `400` `-32020`), stdio (subscription ids, cancellation), and `McpEventsClient` (`subscribe` by push and by poll, over HTTP and stdio, failing on `terminated`). `ConformanceSpec.testServer` serves Events fixture types with the `events_conformance_yield_error` / `_yield_gap` / `_terminate` controls for the not-yet-published conformance scenarios (PR 521: `events-discovery`, `events-poll`, `events-push`), run with `ConformanceServerMain`
- `McpWebhooksSpec` — for webhook delivery (`McpEvents.withWebhooks`, `McpWebhookStore`, `McpWebhookConfig`): `events/subscribe` verification handshake and its `challenge_failed` refusal, signed deliveries (Standard Webhooks, recomputed in the test) with `X-MCP-Subscription-Id` and the watermark cursor, refresh (same id, no new verification, `deliveryStatus`, dual signing after a new secret), retries with the same `webhook-id` and no retry on `410`, `events/unsubscribe` and its `-32023` for an unknown subscription, TTL expiry, `terminated` envelopes, resuming subscriptions from the store, no-expiry grants, suspension (a rezilience circuit breaker, reactivated by a refresh) and the POST bulkhead (`-32025` for a verification past its queue), limits and the per-host verification limit, TLS verification (a self-signed `src/test/resources/webhook-tls/self-signed.p12`), the token-free check context, anonymous subscriptions (`anonymous = true`: verified every time, a new secret only after the endpoint verifies it), the compatibility modes (`McpEventsCompatibility`: by default the spec for every client, ChatGPT included; with `KnownClients`, ChatGPT's dialect for a 2025 session from `openai-mcp` with `capabilities.events`, `-32015`, `webhook-id` = `eventId`, no `terminated` envelope, other clients on 2025 getting `-32601`, and on 2026-07-28 by `User-Agent` until the client declares the extension; `capabilities.events` for everyone; the `eventId` as `webhook-id` for clients that don't declare the extension and for `tanstack-ai-mcp`; `Mcp-Name` optional), and refusals (no principal, bad secret, `http` and local targets, poll-only types). `TestWebhookStore` is the in-memory store the tests use
- `TachyonInteropSpec` — for cross-implementation interop against the third-party `kpavlov/tachyon` server (modern negotiation + legacy interop, and our client following tachyon's Tasks-extension tasks via `tachyon-extensions-tasks`)
- `AiSdkEventsSpec`, `TanStackEventsSpec`, `MastraEventsSpec`, `PythonEventsSpec` — for webhook delivery to the MCP clients that implement MCP Events, end to end: `@ai-sdk/mcp` 2.0.103, `@tanstack/ai-mcp` 1.3.1 and `@mastra/mcp` 2.10.0 against a server with `KnownClients` (Mastra's is also refused by the spec default, for its missing `Mcp-Name`), and the Python MCP SDK's unreleased Events client (python-sdk PR 3822, pinned to commit `a5e0630`) against the spec default. Each subscribes with a webhook on its own `127.0.0.1`, passes the challenge, gets the event in its receiver and unsubscribes. `EventsClients` runs `src/test/resources/mcp-events-js/probe.mjs` (versions pinned by its `package-lock.json`, in `node:22-slim`) or `src/test/resources/mcp-events-python/probe.py` (in `python:3.12-slim`) in a container on the host network, so these are ignored where host networking isn't available. Needs Docker and network for `npm ci`, `git clone` and `pip install`
- `PythonSdkSpec` — for bearer-only servers seen by a Python client: the official Python MCP SDK (`mcp` 1.30.0 on httpx 0.28.1, the stack of claude.ai's connector check) in a container against `StaticBearer` (no token → `McpError` -32001 with our message and no OAuth attempt; wrong token; right token initializes and lists tools; `open = Handshake` initializes without a token and then `tools/list` raises the error). Needs Docker. `DockerSupport` holds what it shares with `ConformanceSpec` (the host's proxy CA, host vs bridge networking)
- `ParameterizedMountAudienceCompatSpec` — the `McpAuth.acceptOriginAudience` quirk: by default a token whose `aud` is only the host origin is refused on a parameterized mount, with the quirk it's accepted, and the exact per-mount audience works either way
- `AsMetadataOriginSpec` — an auth server with a cross-origin authorization server serves no authorization-server metadata on its own origin, for any `User-Agent` (the old kiro-cli 302 redirect is gone), and its protected resource metadata names the authorization server
- `KiroCliDiscoverySpec` — whether the installed kiro-cli finds a cross-origin authorization server through the protected resource metadata alone (why the old AS-metadata redirect could go, and the check to rerun on a new kiro-cli): the real kiro-cli, on both engines (`--v3`, user agent `node`; `--v2`, `kiro-cli/<version>`), against a parameter-mounted auth server with a cross-origin `TestIdp`, recording its discovery requests. It passes when kiro-cli reads the authorization server from the protected resource metadata and never asks the MCP origin for authorization-server metadata. kiro-cli runs in a temporary `HOME` with one trivial `--no-interactive` prompt; the sign-in itself doesn't finish, since kiro-cli opens no browser there. A no-op unless `kiro-cli` is on the `PATH` and signed in
- `McpServerStdioSpec` — for the stdio server examples (`server.serveStdio`, `server.serveStream`): raw JSON-RPC over in-process pipes (request-scoped notifications before the response, concurrency, cancellation, parse errors, `subscriptions/listen` acknowledgement, end of input), and `StdioServerMain` as a subprocess for this library's stdio client (modern and legacy, stdout kept clean) and the official Java SDK's stdio client
- `McpClientStdioSpec` — for the stdio client example (`McpClient.connectStdio`, `McpStdioConfig`) against servers launched as subprocesses: `StdioFixtureServer` (scripted legacy, silent-legacy and modern modes) and `JavaSdkStdioServer` (the official Java SDK's stdio server); covers the discover probe and its timeout (including slow-starting modern and silent legacy servers), server pings, cancellation, a dying server, and forced shutdown
- `McpClientLiveSpec` — for the no-auth client example against the live Java SDK server `https://www.javadocs.dev/mcp`
- `McpClientAuthSpec` — for the client `OAuthClientCredentials` example, exercised against our own auth-protected `McpServer` with tokens minted via DCR at `login.jamesward.dev`
- `CimdAuthSpec` — for the client `OAuthAuthorizationCode` example (authorization-code + PKCE, CIMD, DCR fallback, pre-registration, RFC 9207 `iss` validation, PRM resource validation), exercised in-process against `TestIdp` + our own auth-protected `McpServer` (loopback, no network)
- `LiveCimdAuthSpec` — for CIMD interop against the real `login.jamesward.dev` authorization server (metadata advertisement, client identification by metadata document, rejection of a mismatched or unresolvable document)
- `ClientConformanceSpec` — for the client behaviors graded by the official MCP conformance kit's client scenarios: every scenario of the `2025-11-25` and `2026-07-28` revisions (auth discovery, registration, `iss`, scopes and step-up, authorization-server migration, the `2025-03-26` fallbacks, token endpoint auth methods, `sse-retry`, MRTR, elicitation defaults, JSON Schema, the SEP-2243 standard and `x-mcp-header` headers), `auth/client-credentials-basic`, and the `sep-2640-client-*` Skills scenarios, driving `ConformanceClientMain` as the client-under-test. `ConformanceClientMain` does what each scenario asks (the context's `toolCalls`, `add_numbers`, the schema echo) and answers input with an elicitation's defaults. Not run, because the client doesn't implement them: `auth/client-credentials-jwt`, `auth/dpop`, `auth/dpop-nonce`, `auth/enterprise-managed-authorization`, `auth/wif-jwt-bearer`

When adding or modifying a README example, add or update the matching test in the appropriate spec.

- Run `./sbta "testOnly *McpClientSpec*"` for client unit tests against our own server (loopback HTTP, no network)

- Run `./sbta "testOnly *AiSdkEventsSpec* *TanStackEventsSpec* *MastraEventsSpec* *PythonEventsSpec*"` for MCP Events webhook delivery to the JavaScript and Python clients (requires Docker with host networking, and network for `npm ci`, `git clone` and `pip install`)
- Run `./sbta "testOnly *KiroCliDiscoverySpec*"` to check the installed kiro-cli's authorization-server discovery (needs `kiro-cli` signed in; sends one prompt per engine; tagged `kiro-cli`)
- Run `./sbta "testOnly *McpServerStdioSpec*"` for the stdio server, in-process and as a subprocess on the test classpath (no network)
- Run `./sbta "testOnly *McpClientStdioSpec*"` for the stdio client against subprocess servers on the test classpath (`test.classpath`, set in `build.sbt`; no network)
- Run `./sbta "testOnly *McpClientLiveSpec*"` for the no-auth client test against `www.javadocs.dev` (requires network; tagged `live`)
- Run `./sbta "testOnly *McpClientAuthSpec*"` for the client OAuth `client_credentials` test against our own auth server + `login.jamesward.dev` (requires network; tagged `live-auth`)
- Run `./sbta "testOnly *CimdAuthSpec*"` for the client authorization-code + PKCE + CIMD flow against the in-process `TestIdp` (loopback, no network)
- Run `./sbta "testOnly *ClientConformanceSpec*"` for the official conformance kit's *client* scenarios against our `McpClient` (requires `npx`/Node and npm-registry network access; tagged `conformance-client`)
- Run `./sbta "testOnly *LiveCimdAuthSpec*"` for CIMD interop against `login.jamesward.dev` (requires network; tagged `live-auth`). A CIMD document must be served from a public HTTPS URL matching its own `client_id`, so the spec mints one per test from the CIMD test server: `https://www.cimd.now/<port>/<path>` returns a document whose `client_id` is that URL and whose `redirect_uris` is `http://localhost:<port>/<path>`. Set `CIMD_TEST_SERVER` to point at another deployment — note that sbt's server pins environment variables at startup, so run `./sbta shutdown` first when changing it
- Run `./sbta "testOnly *NegotiationSpec* *TasksSpec*"` for protocol version negotiation and Tasks-extension unit/HTTP tests (no network)
- Run `./sbta "testOnly *McpClientModernSpec*"` for the modern (2026-07-28) client negotiation tests against our own dual-era server (loopback, no network)
- Run `./sbta "testOnly *TachyonInteropSpec*"` for third-party interop against `kpavlov/tachyon` (loopback, no external network; JDK 21+)
- Run `./sbta "testOnly *ConformanceSpec*"` for MCP conformance tests (requires Docker; no Node on the host). Runs the `2025-11-25` kit (`0.1.x`, pinned) and the `2026-07-28` kit (`0.2.0` line) — both are hard checks now that the `2026-07-28` spec is final
- The modern run uses the kit's `--requirements 2026-07-28` mode (kit `0.2.0-alpha.11`+; pinned to `0.2.0-alpha.12`, as `ClientConformanceSpec` is), which runs exactly the scenarios that revision requires from its frozen manifest. That is the only mode that reaches the `input-required-result-*` (MRTR) scenarios: they were pending in the kit's own suite when the revision shipped, so the default `active` suite skips them. The legacy run stays on `--spec-version`, which is all the `0.1.x` line understands
- The MRTR scenarios drive named fixtures on the test server (`test_input_required_result_*` and the `test_input_required_result_prompt` prompt). The names, the input-request keys, and the `state-ok` marker are fixed by the suite — read the scenario descriptions (`conformance list`, or the scenario's `description`) before changing one
- Nothing is baselined on host networking: `server-stateless` (SEP-2575) passes against its fixtures `test_missing_capability`, `test_streaming_elicitation` and `test_logging_tool`, and `http-custom-header-server-validation` against `test_param_headers` (names fixed by the kit). The kit's not-scored scenarios (scenarios added after the revision shipped) run and report but never count, so they need no baseline
- The `sep-2640-skills-*` extension scenarios run, like the Tasks ones, one at a time under `--force`, on both eras, in a fourth `ConformanceSpec` test, against `conformanceSkills`: this build's own test skills, loaded from the test resources alone, because the kit reads the first listed skill's directory and needs a subdirectory in it
- The `tasks-*` extension scenarios are off the spec timeline, so `--requirements` never runs them; a third `ConformanceSpec` test runs each listed in `TasksScenarios` with `--scenario <name> --force` against the `greet` / `slow_compute` / `failing_job` / `protocol_error_job` / `confirm_delete` / `multi_input` fixtures (names fixed by the kit) and fails on any failed check except `wire-schema-valid`, which validates `CreateTaskResult` against the core `CallToolResult` schema and so cannot pass. `tasks-mrtr-composition` (MRTR before task creation) is not supported
- Run the kit without Docker — a host with Node but no daemon, or to iterate on one scenario — by serving the same fixtures directly: `./sbta "Test/runMain com.jamesward.ziohttp.mcp.ConformanceServerMain"` (port 3000, override with `PORT`), then `npx @modelcontextprotocol/conformance@<version> server --url http://localhost:3000/mcp --requirements 2026-07-28`. `ConformanceSpec` remains the checked-in run: it pins the versions and the baseline
- The kit runs in a testcontainer built from `node:22-slim` with the kit preinstalled, so the host needs nothing but Docker. On Linux the container joins the host network namespace and reaches the server at a real `localhost` URL, which lets `dns-rebinding-protection` run and keeps the expected-failures baseline empty — every scenario is expected to pass. Elsewhere it falls back to bridged networking via `host.testcontainers.internal`, where that one scenario is baselined. Force a mode with `CONFORMANCE_HOST_NETWORK=true|false`
- If the host sits behind a TLS-intercepting proxy, the image build picks up its CA from the standard environment variables (`NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`) and trusts it, so `npm install` does not fail the build with `SELF_SIGNED_CERT_IN_CHAIN`. On a machine with none of those set, the build is unchanged

## Shared Test Helpers

`AuthTestHelpers` (in the test source tree) provides DCR + token-fetch + auth-server-build helpers used by `LiveAuthSpec`, `JavaSdkAuthSpec`, and `McpClientAuthSpec`. Reuse these rather than duplicating helper code when adding new auth integration tests.

It also provides `retryTransientUpstream`, a `TestAspect` applied to every spec that talks to a hosted service. It retries a test up to 3 times with exponential backoff, but **only** when the failure text looks like a transient outage (`ServiceUnavailable`/`503`, `502`, `504`, dropped or timed-out connections). Assertion failures and other runtime errors are never retried, so a real regression still fails on the first attempt. Add it to new specs that depend on an external host; don't add it to offline specs, where a flake is a bug worth seeing.

`TestIdp` (in the test source tree) is a minimal in-process OAuth 2.1 authorization server for client-side auth flow tests: RFC 8414 metadata, auto-approving `/authorize` with CIMD dereferencing and configurable RFC 9207 `iss` behavior, PKCE-verifying `/token` minting RS256 JWTs (validated via `discoverJwks`), optional DCR, and recorded events for wire-level assertions. Used by `CimdAuthSpec`; reuse it for new client-side auth tests.

`ConformanceServerMain` (in the test source tree) serves `ConformanceSpec.testServer` on a fixed port so the kit can be pointed at it without Docker.

`ConformanceClientMain` (in the test source tree) is the client-under-test entrypoint for the conformance kit's client mode; it reads `MCP_CONFORMANCE_SCENARIO` / `MCP_CONFORMANCE_CONTEXT` / `MCP_CONFORMANCE_PROTOCOL_VERSION` and picks the matching `McpClientOAuth` config.
